# PORTAL 3.2 — проект миграции идентичности и финансовых фактов

Дата проектирования: 2026-09-27. Основание: текущее рабочее дерево поверх `1fa78b0`, включая незакоммиченные изменения Stage 6. Это проект, не разрешение применять миграции или переключать production. SQL и сервер здесь не запускались; реальные данные, тарифы, закрытые снимки и версия приложения не менялись.

## 1. Вывод и блокирующие факты

`employee_id` пока лишь имя API для `employees.telegram_id`: `with_employee_id()` копирует значение, `save_user()` переносит его обратно, `Repository.catalog('users')` делает то же. Новые локальные сотрудники получают отрицательный `telegram_id`; это доказывает, что колонка уже не означает Telegram account. Устойчивая отдельная сущность сотрудника отсутствует.

Работа `/api/v3/work` в одной транзакции создаёт `work_log` и `portal_production(kind='works')`, связывая их через `works.legacy_id`. `/api/work` при готовом production перенаправляется туда же, но старые `/api/work/mine`, `/api/payroll/mine`, dashboard и карточка клиента читают `work_log`. Закрытие `/api/v3/payroll-periods` считает только `works`; значит историческая работа, внесённая до ledger, не входит в закрываемый снимок без явного backfill. Сложение обоих источников удвоит новые работы. Текущее закрытие группирует по `user_id`, а выплаты — по `employee_id`: несколько аккаунтов одного работника могут разделить начисление.

В текущем дереве уже появились `payroll_settlement_entries`, `/api/v3/payroll-settlements` и Stage 6 SQL. Поэтому baseline-фраза «выплат нет» устарела: есть append-only выплаты, корректировки и сторно в копейках. Но legacy `/api/payroll/mine` продолжает читать `payroll_transactions`, период закрытия — `portal_production`, а PostgreSQL Stage 6 FK ссылается на `employees(company_id,telegram_id)`. Согласованный перенос старых выплат и единый read model ещё не доказаны. `postgresql_runtime.sql` также создаёт settlement-таблицу, поэтому до реализации нужен единый порядок и проверка идентичности определений Stage 6/runtime.

Production backend, актуальная схема и grants удалённой БД в репозитории не подтверждены. По умолчанию сервер использует SQLite. Live PostgreSQL/VPS тесты в baseline пропущены. **Любое применение к реальной БД — NO-GO до отдельного cutover-проекта и разрешения оператора.**

## 2. Целевая модель идентичности

| Сущность | Ключ и ограничения | Смысл и жизненный цикл |
|---|---|---|
| `app_users` | `(company_id,id)`; уникальный нормализованный login внутри компании; nullable `employee_id` с FK `(company_id,employee_id)` | Только вход, роль, состояние доступа, PIN/session. Деактивация отзывает сессии; не удаляет сотрудника и историю. Несколько аккаунтов на одного сотрудника — только после утверждения правила; до этого запретить активный дубль частичным unique index. |
| `employees` | `(company_id,employee_id)`; `employee_id` — выделенный сервером bigint/UUID, не вычисляется из Telegram ID или `app_users.id`; `active`, имя, даты | Субъект выработки, зарплаты и назначений. Неактивность блокирует новую работу/назначения, но сохраняет все факты и доступ к исторической сверке. Наличие аккаунта необязательно. |
| `employee_legacy_aliases` | `(company_id,alias_type,alias_value)` unique для разрешённых алиасов; FK на `employees`; индекс `(company_id,employee_id)` | `alias_type='telegram_id'` хранит исходный внешний ID, включая исторический отрицательный surrogate с явной меткой происхождения. Не выдавать новый alias для нового работника. Alias неизменяем после утверждения, конфликт разрешается только через аудируемое сопоставление. |
| `legacy_identity_conflicts` | `(company_id,source_table,source_pk)` unique, статус/причина/кандидаты/решение | Карантин неоднозначных строк. Нельзя привязать к первому попавшемуся сотруднику или использовать глобальное совпадение числа. |

В разных компаниях один и тот же Telegram ID допустим и может вести к разным `employee_id`; любой lookup использует `(company_id,alias_type,alias_value)`. Отсутствующий alias допустим у новых работников. Отсутствующий работник для исторического денежного факта — ошибка сверки: оставить исходную строку неизменной, пометить конфликт, не публиковать новую зарплатную проекцию. Повтор одинакового alias к одному сотруднику дедуплицируется; к разным — карантин/NO-GO. При совпадении alias с уже существующим числовым `employee_id` сравнивать типизированные идентификаторы, а не числа. Внешний API принимает либо `employee_id`, либо временный `telegram_id`; если присланы оба, разрешать каждое отдельно и требовать одинаковый итоговый employee. Старые отрицательные surrogate **не превращать** в Telegram ID в новой модели.

Новые факты хранят `company_id` и `employee_id`; где важно авторство, отдельно `actor_user_id`. Исторический `telegram_id` остаётся исходным полем/alias, но не FK целевых финансовых таблиц. Исторические строки и закрытые snapshots не переписываются; связь хранится в versioned mapping/projection с source PK и checksum. Связь аккаунта с сотрудником редактируется только в своей компании, с отзывом сессий и audit; изменение связи не переносит прошлую выработку.

Формула dedup: `UNIQUE(company_id, source_system, source_table, source_pk)` и `UNIQUE(company_id, legacy_work_log_id)` для связи; каждый v3 `works.legacy_id` должен указывать на единственный `work_log`, и обратное отображение должно быть 1:1. Клиентские invoices/payments и payroll settlements имеют **другие** source registries.

## 5. API, scope и доступ

Общая граница: session определяет компанию; обычный пользователь не меняет её query/body/header. Platform Owner выбирает существующую компанию только явным `X-Portal-Company`, получает технический audit, а не роль директора другой компании. Технический owner `role='admin'` действует лишь внутри выбранного scope. Любой SQL JOIN использует `(company_id,id)`, включая subquery платежа по invoice ID; PostgreSQL RLS — второй барьер, не замена проверке объекта. Для legacy route fallback role убрать только после одинакового решения capability на обоих путях.

| Действие | admin | director | manager | packer |
|---|---|---|---|---|
| Своя работа/зарплата | свои права `work.write`, `payroll.own` при наличии employee | то же | то же, только назначенные клиенты | то же, без клиентской цены |
| Чужая работа/закрытие/settlement | `payroll.all/close/settlement.*` по grant | те же права **только C** | нет по умолчанию | нет |
| Пользователи, сотрудники, permissions | `users.manage` | `users.manage` в C, без прав выше собственных | нет | нет |
| Клиенты/операции/тарифы | `clients.manage`, `rates.*` | то же в C | назначенные клиенты; `rates.client` по grant, не employee rate | доступ к заданиям/операциям без чужой зарплаты/цены клиента |
| Счета/платежи клиента | `invoices.*`, `payments.record` по grant | то же в C | чтение/создание назначенных; payment только override | нет |

`accountant` и `shift` сохраняют точные defaults из `production_permissions.py` и проходят те же company/object checks. Overrides могут убрать/добавить capability внутри компании, но не могут убрать scope или дать системные полномочия. `users.manage` отдельно проверяет запрет эскалации. Матрица — проектная политика; конкретные права manager на платежи и связку нескольких аккаунтов требуют решения ниже.

Проверить **каждый** путь: `/api/login`, `/api/me`, `/api/logout`, `/api/setup`, `/api/company`, `/api/platform/*`; legacy `/api/dashboard`, `/api/clients`, `/api/clients/{id}`, `/operations`, `/api/admin/*`, `/api/users*`, `/api/work*`, `/api/payroll/mine`, `/api/jobs`, `/api/invoices`, `/api/materials`; все `GET/POST /api/v3/{action}` из `Production.query/command` плюс presence/activity/heartbeat. Для каждого фиксировать actor C, SQL C, object owner C, capability, field redaction. Особенно старые JOIN по имени клиента в dashboard/invoices, `WHERE invoice_id=?` в сумме платежей, `work_log WHERE telegram_id=?`, `production_jobs` и `client_invoices` с одинаковым ID у разных компаний.

PG readiness gate до соединения приложения: runtime role `NOSUPERUSER NOBYPASSRLS`, не владелец таблиц и без `SET ROLE` в owner; минимальные `USAGE` schema и DML только нужным таблицам/sequence, никакого доступа к `portal_company_keys`, provision/bind functions для PUBLIC; grant bind только выделенному trusted runtime path. `portal_bind_company` выполняется после начала каждой транзакции через `portal_postgres.Connection` с серверным proof; при выходе контекст сбрасывается, connection pool не наследует C. Проверить `ENABLE` **и** `FORCE RLS`, policy `USING/WITH CHECK portal_current_company()` для каждой tenant таблицы, включая новые alias/source-link/settlement; control tables имеют отдельный доступ. Текущий `postgresql_runtime.sql` для `work_material_consumption` использует raw `current_setting` — привести к защищённому context перед GO. Реальные grants и владелец таблиц не известны из файлов.

## 6. Миграции, сверка и возврат

1. **Инвентаризация без записи:** установить фактический backend/schema version и набор tenant SQLite/control DB, список старых APK/API клиентов, копии и восстановимость backup. Получить только метаданные, не выводить ключи/env. Зафиксировать source cutoff и список таблиц/колонок. Пока эти факты не получены, design остаётся условным.
2. **Offline copy:** согласованная копия каждого tenant файла и control DB; SHA-256 файла, `PRAGMA integrity_check`, count/PK ranges. Запуск существующего `migrate_sqlite_to_pg.py` без `--apply` только над копиями; отчёт хранить вне repo без PII. Ни один путь не указывает на рабочий `portal.db`.
3. **Preflight identity:** построить `(C,telegram_id) → proposed employee_id` из employees, app_users, work_log, assignments, jobs, payroll; явные conflict/orphan отчёты. Не выводить имена/секреты в общий отчёт. Утвердить правила конфликтов; NO-GO при нерешённом денежном факте.
4. **Schema на disposable SQLite/PG:** добавить employee key, alias, identity conflicts и source links без удаления legacy колонок; затем backfill в транзакциях по компании с чекпоинтом/версией. PG порядок: core → stage3 → protected RLS context → stage4c → stage5 → Stage6/runtime в одном установленном порядке → новые identity/FK миграции. Сверить, что Stage6 и runtime не расходятся по FK/check/policy/trigger/marker; не применять два разных определения вслепую. Перевод FK на employee только после backfill и проверки всех ссылок.
5. **Факты:** backfill canonical work только для orphan `work_log`, связать существующие пары по `legacy_id`; периоды/закрытые snapshots копировать неизменными; исторические `payroll_transactions` переносить как маркированные imported settlement facts только после подтверждения значения status/amount. Новые выплаты не выпускать одновременно через старый и новый маршрут. Нормализовать деньги через `Decimal` и integer minor units, сравнивая исходные суммы без изменения округления исторических строк.
6. **Независимая сверка:** отдельный код от импортера, другая реализация расчёта. По каждой C/таблице: counts, список/диапазон PK, anti-joins, количество алиасов/conflicts, 1:1 work links, counts по kind, row hashes и денежные итоги `salary/revenue/direct_cost`, closed snapshot totals, payroll paid/adjustment/balance, invoice due/paid. По периодам и employee сверить копейки; исключить пересечение работ и неизменность снимков. Сверить sequence `max(id)+1`, даты/timezone и права RLS. Любое расхождение — NO-GO.
7. **Dry-run и rehearsal:** повторить на пустой изолированной PG со synthetic компаниями и копиями только при разрешённом тестовом контуре. Прогнать full HTTP/API и UI fixtures, privilege/RLS negative tests, backup/restore и повторный запуск миграции. Dry-run не пишет в source или production.
8. **Cutover отдельным этапом:** freeze writes, новая согласованная копия, import в пустой target, независимая сверка и smoke tests, затем решение оператора. Rollback до открытия writes: вернуть старый endpoint/SQLite snapshot; PG target изолировать, не «откатывать» по частям. После открытия writes нужен заранее утверждённый reverse journal или новый forward fix; простое переключение назад потеряет записи. Closed snapshots никогда не редактировать.

Существующий importer проверяет counts/hash/money по исходным колонкам; этого недостаточно для новой identity семантики, связи legacy/v3 работ и settlement. Его `--apply` уже пишет target и здесь не использовался. PostgreSQL sequence могут не откатываться с транзакцией — повторная попытка только на восстановленном пустом target или с явным пересчётом.

## 7. Payroll state и аудит

Период: `open → closing → closed` (transactional snapshot), при ошибке `closing → open`; после `closed` исходный snapshot неизменяем, запись работы с `completed_at` в диапазоне запрещена обоими API. Reopen не реализовывать по догадке: если утверждён, только новая ревизия/компенсирующая запись с ссылкой на старый снимок и полным audit. Preview не создаёт финансовый факт.

Settlement: `payout` положительный amount, `adjustment` signed entitlement, `reversal` ровно против исходной записи, один reversal на запись. Сохранить `company_id`, employee FK, period FK, actor, timestamp UTC, reason, reference, request ID, source link, amount_minor, currency и audit event. `UNIQUE(C,request_id)` плюс проверка fingerprint на повтор; для payout под lock пересчитать баланс и запретить превышение. Audit и settlement в одной транзакции; не логировать PIN/token или персональные детали сверх необходимого. Историческая выплата импортируется с исходной ссылкой и timestamp, без создания второй выплаты. Клиентский `payments.record` меняет только invoice balance.

Тарифы: `tariff_versions`/ledger tariffs имеют `(C,client_id,operation_id,valid_from,valid_to)`, без перекрытий интервалов; новая работа снапшотит version ID и сумму. Исправление тарифа создаёт новую версию; закрытые/исторические work facts и snapshots не пересчитываются. Корректировка ошибки прошлого — отдельный утверждённый payroll adjustment, не UPDATE старой суммы.

## 8. Тестовая матрица и критерии GO/NO-GO

| Уровень | Обязательные сценарии |
|---|---|
| Identity/unit | Нет alias, два одинаковых в C, одинаковые в A/B, alias ↔ employee numeric collision, отрицательный surrogate, inactive employee, два app_users на employee, оба входных ID совпадают/конфликтуют. |
| Work/payroll | Старый orphan work, v3 mirrored pair, оборванная пара, повтор request ID, разные actor/employee, два аккаунта одного employee, сохранение rate/salary, закрытие и запрет новой работы обоими API, payout/adjustment/reversal, double payout, invoice payment отдельно. |
| API/roles | Каждая группа маршрутов из §5 для admin/director/manager/packer, дополнительно accountant/shift; capability override, field redaction, manager client assignment, owner explicit C/audit, header/query/body spoof. |
| PostgreSQL | Для каждой tenant таблицы `ENABLE/FORCE`, policy, FK и runtime grants; незаданный/подменённый/reused bind; SELECT/INSERT/UPDATE/DELETE A→B; одинаковые PK/alias в A/B; connection reuse. |
| Migration | Empty/reapply/partial, orphan/conflict, counts/PK/hash/money per company, work source links, closed snapshot identity, settlement totals, sequence/timezone, backup restore, rollback rehearsal. |
| Android | Старый и новый JSON, `employee_id` отдельно от alias, работа/зарплата после деактивации, manager/packer UI не раскрывает запрещённые суммы, collision fixtures. |

**GO** только если утверждены бизнес-правила §9, фактическая production конфигурация и backup/restore; ноль unresolved денежно значимых identity conflicts; 100% counts/PK/hash и равенство денежных итогов по компании/периоду/сотруднику; 1:1 каждой mirrored work пары; все scope/RLS/grant negative tests проходят; закрытые snapshots совпадают; старый Android контракт проверен; dry-run, isolated import и rollback rehearsal документированы. **NO-GO** при любом расхождении, неизвестной роли runtime, неготовом RLS/grants, неясном source of truth, пропущенном PG тесте, несовместимом Stage6/runtime DDL, неизвестной семантике старой выплаты или отсутствии восстановимой копии. Прохождение SQLite unit suite само по себе не GO.

## 9. Решения, которые нельзя угадывать

1. Может ли один сотрудник иметь несколько активных login, а один login менять employee? Как показывать старый closed snapshot, сгруппированный по `user_id`?
2. Что означают разные исторические `payroll_payments.status` и `payroll_transactions.amount`: фактическая выплата, закрытие или корректировка? Как обрабатывать отрицательные/дубли?
3. Нужны ли выплаты сверх начисления, авансы, перенос остатка между периодами, валюты помимо RUB и округление исторических дробных сумм?
4. Кто утверждает корректировку, сторно, reopen периода и какой порог/основание; разрешено ли исправлять уже оплаченный период и как это отражать в отчёте?
5. Какой источник authoritative для старых client invoices/payments при наличии ledger копий, и как сопоставлять их без повторного признания revenue?
6. Какой срок совместимости старых APK и старых полей `telegram_id`; можно ли возвращать alias там, где его нет?
7. Разрешён ли director управление payroll/users/tariffs по defaults текущего каталога; manager payment override; как отображать owner technical actions в аудите компании?
8. Подтверждённые production backend, schema markers, миграционный оператор, grants, backup retention, окно freeze и rollback после новых записей.
