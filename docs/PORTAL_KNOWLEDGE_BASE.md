# PORTAL Knowledge Base
Версия: 1.0
Дата: 2026-09-30
Назначение: постоянный бизнес- и продуктовый контекст для Codex и всех следующих этапов PORTAL.

## 1. Кто мы
PORTAL — фулфилмент-компания в Пятигорске, Ставропольский край. Мы обслуживаем продавцов маркетплейсов и других клиентов, которым нужны повторяемые складские операции.

Основные направления:
- приёмка и проверка товара;
- хранение и движение остатков;
- маркировка, стикеровка и сортировка;
- упаковка и комплектация;
- FBS/FBO и подготовка к отгрузке;
- обработка возвратов;
- контроль качества;
- документы, расчёты, счета и управленческий учёт.

Идея PORTAL: соединить людей, операции, деньги и контроль в одном понятном процессе.

## 2. Высший принцип
Действуй в интересах PORTAL так, чтобы обеспечить максимальную долгосрочную прибыль, рост и устойчивость компании, не нарушая закон.

Практические следствия:
- не создавать бюрократию без пользы;
- считать экономику, а не только объём;
- объём не оправдывает ухудшение качества;
- короткая экономия не должна разрушать качество и устойчивость;
- успешные решения масштабировать, неэффективные быстро менять или останавливать;
- автоматизация должна уменьшать зависимость от памяти и одного человека.

## 3. Культура PORTAL
- Думай, а не просто исполняй.
- Увидел проблему — сообщи и предложи решение.
- Не скрывай ошибку: причина → последствия → исправление → защита от повторения.
- Бери ответственность за свою зону.
- Помогай другим подразделениям.
- Добросовестно останавливай опасный процесс, если продолжение способно нанести существенный ущерб.
- Полезная инициатива должна вознаграждаться и не блокироваться должностью.
- Ни один критический процесс не должен зависеть только от одного человека.
- Отчётность должна помогать принимать решения, а не существовать ради отчётности.

Базовый управленческий цикл:
проблема/решение → ответственный → срок → ожидаемый результат → фактический результат.

## 4. Бизнес-управление и программные роли — не одно и то же
### Бизнес
- Собственник определяет стратегию и сохраняет высшую власть.
- Эрнест — основной операционный руководитель/заместитель собственника; строит систему, где собственнику не нужно погружаться в ежедневную операционку.
- Управляющий складом отвечает за экономику, качество и работу своего подразделения.

### В приложении
- Platform Owner: Ernest — глобальный владелец SaaS.
- Директор — полный контроль только внутри своей компании.
- Менеджер — управленческие функции + возможность вносить собственную выработку.
- Сотрудник/упаковщик — рабочие операции и собственная выработка по разрешениям.
- Старший смены/бухгалтер и похожие роли формируются capabilities/permissions, а не обходят авторизацию.

Обычный лимит компании — до 15 активных пользователей/сотрудников; расширение с 16-го решает Platform Owner. Для компании PORTAL лимита нет.

## 5. Текущая архитектура продукта
Старый Telegram-бот закрыт и не является текущей платформой.

Цель:
- Android APK — тонкий мобильный клиент;
- Desktop/Web — полноценный ПК-интерфейс;
- центральный VPS;
- PostgreSQL — центральное хранилище бизнес-данных;
- защищённый API;
- сервер — источник истины по правам, tenant isolation и финансовому состоянию.

APK не хранит мастер-БД компании, production credentials, API secrets, DB passwords, private signing material или скрытый master login.

Локальное Android-хранилище допустимо для безопасного кэша и переходного хранения документов, но не как основная бизнес-БД.

## 6. Обязательный pipeline
Код → GitHub → CI/сборка → изолированный тестовый VPS/PostgreSQL → проверки → готовый APK/artifact.

Телефон:
- не компилирует;
- не гоняет автоматические тесты;
- не является ADB release gate;
- его отсутствие не блокирует разработку;
- используется только для установки готового APK и просмотра как обычным пользователем.

Production DB и реальные финансовые данные никогда не являются тестовой средой.

## 7. Multi-company и безопасность
- company/tenant isolation — fail-closed;
- сервер проверяет права на каждую защищённую операцию;
- нельзя доверять company_id, присланному клиентом, без проверки прав;
- PostgreSQL isolation/RLS применять где предусмотрено архитектурой;
- финансовая и документная история должна быть аудируемой;
- append-only/revision там, где переписывание истории опасно;
- секреты не попадают в Git/APK;
- private SSH/signing keys не коммитятся;
- действия Platform Owner имеют отдельный owner-аудит;
- ежедневный backup сервера, хранение 14 дней, плюс проверка restore до production cutover.

## 8. Основные модули

### Зарплата
- сумма за выбранный период;
- выбор сотрудника;
- диапазон с/по;
- быстрые периоды: сегодня, неделя, 1–15, 16–конец, месяц;
- детализация выработки;
- закрытые периоды сохраняют финансовую правду;
- краткий расчётный лист без детализации по клиентам/операциям.

Поля расчётного листа: компания, «Расчётный лист», период/год, ФИО, итоговая сумма, дата.
Подписи строго:
1. Управляющий компанией
2. Управляющий подразделением
3. Сотрудник

### Склад расходных материалов
Итого/Обзор, Остатки, Поставка/Приход, Добавить материал, Взять материал/Списание, Корректировка, История движений.
Два режима списания:
1. сотрудник сам берёт и списывает;
2. менеджер/завсклад выдаёт и списывает.

### Счета
- задолженность/аванс;
- «Нам должны» и «Авансы»;
- полноценный «Счёт на оплату» с реквизитами;
- строки: операция, количество, цена, сумма;
- итоговая сумма;
- сформированный счёт заблокирован;
- admin/director может «Отправить на редактирование»;
- manager редактирует только в editing;
- новая финальная версия создаёт revision, не переписывая исходный финансовый факт.

### Клиенты
В карточке клиента есть блок «Операции и тарифы»:
- операция;
- ставка сотруднику;
- цена клиенту при необходимости;
- active/archive;
- добавление/редактирование по правам.

### Документы
Цель — центральное хранилище:
- компания/клиент/сотрудник/тип/дата;
- поиск и фильтры;
- права;
- история;
- XLSX/PDF;
- расчётные листы;
- счета;
- отчёты;
- скачать/сохранить/поделиться/email.

Переходный этап допускает локальное сохранение документов Android до завершения Desktop/Web; конечная модель — централизованное хранение/синхронизация.

### Excel импорт/экспорт
Стандартный шаблон минимум:
- Компания
- Сотрудники
- Клиенты
- Операции/Тарифы

Доступ: Platform Owner и директор своей компании.
Поток: получить шаблон → сохранить/поделиться/email → загрузить заполненный → preview → validation → защита от дублей → confirm → transactional commit только в выбранную компанию → итоговый отчёт.

### Новости
Разделы Ozon и Wildberries. Только официальные источники. Дубли исключать. Demo/preview-контент всегда явно маркировать и не выдавать за реальные текущие новости.

### Внутренний чат
Цель: общий чат компании, личные комнаты, текст, разрешённые вложения/фото, закрепления, системные сообщения и заданное хранение истории. Реальный статус брать из последнего roadmap/report, не из этого файла.

## 9. Управленческие отчёты
Интерфейс и отчёты должны помогать действовать, а не просто показывать цифры:
- выручка;
- операционная прибыль;
- маржа;
- обработанные единицы;
- ФОТ / выручка;
- дебиторка и просрочка;
- расходы;
- ошибки/качество;
- открытые управленческие решения;
- план/факт и KPI.

Каждый склад рассматривается как отдельная экономическая единица. Управляющий должен видеть выручку, объём, ФОТ, аренду, логистику, расходники, прочие расходы, дебиторку и финансовый результат.

## 10. Подписки и компании
Platform Owner может:
- создавать компании;
- назначать директоров;
- включать/выключать модули;
- задавать индивидуальную абонплату;
- задавать demo period в днях;
- активировать/приостанавливать доступ;
- выполнять поддержку в рамках owner-аудита.

Demo-режим полнофункциональный на установленный срок, если более новое ТЗ не изменило это правило.

## 11. UI-философия
- современно, чисто, понятно;
- интерфейс зависит от роли;
- главная показывает самое важное за несколько секунд;
- частые действия сотрудника — минимум нажатий;
- крупные элементы на Android/ТСД;
- никаких «мёртвых» кнопок: работает, открывает явно помеченный Preview или объясняет статус;
- fake/demo data нельзя выдавать за production;
- пользовательские ошибки не показывают stack trace, SQL и secrets;
- приветствие зависит от локального времени;
- главный экран директора должен давать картину компании примерно за 3–5 секунд.

## 12. Release и версия
Нумерация новых сборок: 3.0, 3.1, 3.2, ... 3.9, 4.0 и далее.
Каждая новая сборка получает уникальный видимый номер.
Не повышать production APK/versionCode как побочный эффект несвязанной задачи.
Production Android signing использует один стабильный release identity; приватный ключ и пароли никогда не попадают в Git.

## 14. TalAnt / WMS
Это отдельный интеграционный контур.

PORTAL = интерфейс сотрудников и бизнеса.
TalAnt = WMS-ядро и шлюз к WB/Ozon там, где это предусмотрено.

Правила:
- только официальный API/интеграционный слой;
- без прямого доступа к БД TalAnt;
- без изменения исходного кода TalAnt;
- для каждого типа данных определить system of record;
- операция PORTAL, зависящая от TalAnt, считается завершённой только после требуемого подтверждения TalAnt.

ТСД:
- Android-ТСД;
- аппаратный сканер;
- штрихкоды/GTIN;
- при необходимости DataMatrix/КИЗ;
- маленький экран, крупные элементы управления, минимум нажатий и быстрый повторный поток сканирования.

## 16. Протокол Codex
Перед задачей: AGENTS.md → Knowledge Base → Constitution → Master Roadmap → текущее ТЗ → последний report/tests/code.

Во время задачи:
- работать только в назначенной ветке/worktree;
- соблюдать DO NOT TOUCH;
- не расширять scope молча;
- сохранять tenant isolation и финансовую неизменяемость;
- добавлять тесты при изменении поведения;
- использовать изолированную тестовую инфраструктуру;
- не использовать телефон как test runner.

После задачи:
- targeted tests;
- широкий релевантный suite;
- compile/syntax checks;
- git diff --check;
- зафиксировать skipped/risks;
- обновить/создать requested report;
- оставить clean working tree, если этого требует ТЗ.
