# PORTAL — UI Blueprint для Preview APK

**Статус:** утверждённая рабочая основа для первой и последующих preview APK.  
**Дата фиксации:** 28.09.2026.  
**Назначение:** сделать тестовую APK визуально максимально близкой к будущей итоговой программе, даже если часть backend-функций ещё не подключена.

## 1. Главный принцип preview APK

Preview APK — не «урезанная техническая сборка», а живой макет конечного продукта. Пользователь должен иметь возможность пройти глазами почти всю будущую систему: открыть разделы, увидеть карточки, формы, кнопки, навигацию, состояния и логику переходов.

Каждый пункт интерфейса обязан находиться в одном из трёх состояний:

- **LIVE** — функция реально работает с API и данными.
- **PREVIEW** — полноценный визуальный экран с тестовыми/демо-данными и заметной меткой «Preview / В разработке».
- **FUTURE** — только для функций, которые ещё нельзя корректно визуализировать; кнопка не должна быть «мёртвой», она обязана открывать экран-описание будущего модуля.

Запрещено: молча неработающие кнопки, фиктивные финансовые цифры без маркировки, имитация production-действий, случайное скрытие уже согласованных модулей.

## 2. Общая навигация продукта

Целевая верхнеуровневая структура Android / Desktop / Web:

1. Главная
2. Работа
3. Клиенты
4. Сотрудники
5. Зарплата
6. Финансы
7. Документы
8. Склад / WMS
9. Чат
10. Отчёты
11. Новости
12. Настройки

На телефоне основная нижняя навигация остаётся компактной: **Главная / Работа / Ещё / Настройки**, а остальные разделы открываются через «Ещё» и быстрые карточки.

## 3. Роли и варианты главного интерфейса

### Platform Owner

Главная задача — управление платформой, компаниями и технический доступ.

Экраны: компании, создание/редактирование компании, директор компании, статус сервиса, демо-период, абонплата, лимит пользователей, включение модулей, аудит владельца, технический вход в выбранную компанию, состояние API/backup/версий.

### Директор

Главная задача — полный контроль внутри своей компании.

Видит все бизнес-модули компании: сотрудники, клиенты, тарифы, производство, зарплата, склад, счета, оплаты, документы, финансы, отчёты, чат, настройки компании.

### Менеджер

Главная задача — операционное управление и собственная выработка.

Видит назначенных клиентов, операции, задания, партии, выработку, счета в рамках прав, чат, документы и разрешённую аналитику.

### Сотрудник / упаковщик

Главная задача — быстро выполнить рабочее действие.

Рекомендуемая мобильная навигация: **Главная / Работа / Моя выработка / Чат / Ещё**. Минимум текста, крупные кнопки, частые действия за 2–3 нажатия.

### Старший смены / бухгалтер

Экран формируется по разрешениям: склад, сотрудники смены, зарплата/выплаты, документы, счета/оплаты, чат и отчёты согласно server permissions.

## 4. Главный экран директора — PORTAL Сегодня

Главный экран директора должен давать картину компании за 3–5 секунд.

Порядок блоков:

1. **Шапка** — PORTAL, компания, дата, профиль/уведомления.
2. **Сегодня** — выработка за день, выполнено единиц, сотрудников работало, начислено сотрудникам, краткий статус дня.
3. **Требует внимания** — просроченные счета, низкие остатки, проблемы документов, незакрытые периоды, ошибки/предупреждения.
4. **Финансы** — выручка, ФОТ, материалы, прочие расходы, прибыль/маржа только при достоверных данных.
5. **Зарплата** — начислено, выплачено, остаток, статус текущего периода.
6. **Дебиторка** — нам должны, просрочено, количество должников, 2–3 проблемных клиента.
7. **Производство** — активные партии/задания, завершено, ожидает, узкие места.
8. **Быстрые действия** — Сотрудники, Клиенты, Склад, Счета, Зарплата, Документы, Отчёты, Настройки.

Визуальная иерархия: «Сегодня» и «Требует внимания» самые заметные; затем деньги/зарплата/дебиторка; потом производство и быстрые действия.

## 5. Дизайн-система

Общий стиль: современный спокойный business UI, визуально дорогой, без ощущения «старого бухгалтерского ПО».

- Светлый чистый фон; обязательная поддержка тёмной темы.
- Карточки с мягкими скруглениями и нормальными отступами.
- Крупные ключевые цифры, вторичная информация визуально спокойнее.
- Минималистичные иконки.
- Одна основная фирменная акцентная гамма + нейтральные тона.
- Статусы: зелёный = норма, жёлтый/оранжевый = внимание, красный = проблема, нейтральный = информация.
- Не превращать интерфейс в «светофор».
- Крупные зоны нажатия, управление одной рукой.
- На главных экранах — никаких длинных таблиц и перегруженных форм.

## 6. Экран «Работа»

### LIVE / целевой вид

- Выбрать клиента.
- Выбрать операцию.
- Ввести количество.
- Показать ставку и ожидаемое начисление.
- Записать работу.
- Показать последние записи.
- Сохранить последний выбор.

### Расширение preview

- Активное задание.
- Таймер старт / пауза / продолжить / завершить.
- «Другая работа» без задания.
- Привязка работы к партии.
- Сканирование товара для WMS/ТСД как отдельный preview-поток.

## 7. Клиенты — Client 360°

Карточка клиента должна содержать:

- название и статус активен/архив;
- реквизиты: ИНН, КПП, юр. название, БИК, к/с, р/с, контактное лицо, телефон, email;
- операции и тарифы;
- ставка сотруднику;
- цена клиенту;
- история тарифов / дата начала действия;
- статистика: объём, выручка, счета, задолженность;
- активные партии/задания;
- документы клиента;
- расходы клиента;
- финансовый радар / маржа;
- связанные товары/номенклатура.

В preview APK все вкладки Client 360° должны быть видны, даже если часть пока PREVIEW.

## 8. Сотрудники — Employee 360°

Карточка сотрудника:

- ФИО, логин, роль, статус;
- привязка к employee_id;
- права и индивидуальные разрешения;
- история входов;
- Online / Offline;
- выработка;
- зарплата;
- выплаты/корректировки;
- текущие задания;
- документы;
- история активности.

Два сценария создания доступа сохраняются визуально и функционально:

- «Создать нового сотрудника»;
- «Выдать доступ существующему сотруднику».

## 9. Зарплата

Целевые экраны:

- Моя зарплата.
- Зарплата по сотруднику.
- Выбор периода «с–по».
- Быстрые периоды: сегодня, неделя, 1–15, 16–конец, месяц.
- Начислено / выплачено / остаток.
- Расчётные периоды preview → закрытие → immutable snapshot.
- Выплата.
- Корректировка.
- Сторно.
- История выплат.
- Печатный расчётный лист A4.

Расчётный лист: компания, «Расчётный лист», период/год, ФИО, итоговая сумма, дата, подписи в порядке: Управляющий компанией → Управляющий подразделением → Сотрудник.

## 10. Финансы

Экраны:

- финансовый радар;
- выручка;
- ФОТ;
- материалы;
- расходы;
- прибыль;
- маржа;
- прибыль по клиенту;
- прибыль по партии;
- динамика по месяцам;
- дебиторка;
- просрочки;
- блок «Требует внимания».

Недостоверные показатели не показывать как реальные: либо скрывать, либо маркировать как preview.

## 11. Счета и оплаты

Целевой раздел должен включать два уровня:

### Простая сводка

- «Нам должны»;
- «Авансы»;
- неоплачено / частично оплачено / оплачено;
- просрочено;
- история оплат.

### Полноценный «Счёт на оплату»

- реквизиты клиента;
- реквизиты исполнителя;
- табличная часть: операция, количество, цена, сумма;
- автоматический итог;
- сохранение цены в строке счёта;
- создание Excel/PDF;
- после формирования счёт блокируется;
- директор/админ: «Отправить на редактирование»;
- менеджер может исправлять только после разрешения.

В preview APK форма и просмотр счёта должны существовать визуально, даже если генератор файла ещё PREVIEW.

## 12. Склад материалов

Обязательные вкладки:

- Итого / Обзор;
- Остатки;
- Поставка / Приход;
- Добавить материал;
- Взять материал / Списание;
- Корректировка;
- История движений;
- Минимальные остатки / предупреждения.

Два режима списания:

1. сотрудник сам берёт материал и списывает;
2. менеджер/завсклад выдаёт материал и списывает.

- Ячейки;
- Приёмка;
- Размещение;
- Перемещение;
- Подбор;
- Сборка;
- Упаковка;

3. Сохранить на устройство.
4. Поделиться/Отправить.
5. Отправить по email.
6. Загрузить заполненный файл.
7. Preview изменений.
8. Validate.
9. Проверка дублей.
10. Confirm.
11. Transactional Commit только в выбранную компанию.
12. Итоговый отчёт импорта.

Доступ: Platform Owner и директор своей компании.

## 22. Обновление APK

Целевой UX:

- текущая версия;
- доступная версия;
- номер сборки;
- changelog;
- кнопка «Скачать обновление»;
- проверка SHA-256;
- запуск Android-установщика;
- единый постоянный release-key;
- все следующие production APK подписываются тем же ключом.

До создания production key пароль должен быть не менее 16 символов; после создания обязательно проверить фактическое наличие и валидность `portal-release.p12`.

## 23. Backup и безопасность

До production cutover обязательны:

- ежедневный backup PostgreSQL;
- хранение 14 дней;
- вторичная/off-server копия;
- проверка restore;
- журнал backup;
- production HTTPS;
- RLS;
- fail-closed company isolation;
- секреты только на сервере/GitHub Secrets;
- APK не содержит БД компании, пароли и API-секреты.

В текущем VPS-аудите отдельный PORTAL backup timer/service отсутствует — это обязательный gate до production.

## 24. Поведение PREVIEW-экранов

Каждый неготовый модуль обязан:

- открываться;
- выглядеть как будущий реальный экран;
- иметь демонстрационные карточки/формы;
- иметь заметную метку «Preview»;
- не писать в production;
- не подставлять фиктивные данные как реальные;
- позволять оценить навигацию, размеры, тексты, кнопки и общий UX.

## 25. Состояния кнопок

Разрешены только три поведения:

1. Работает и выполняет действие.
2. Открывает preview-поток / экран.
3. Открывает карточку «Функция готовится» с описанием и будущим сценарием.

Запрещено: нажал — ничего не произошло.

## 26. Проверка каждой preview APK

Перед публикацией GitHub Artifact проверить:

- версия и номер сборки уникальны;
- сборка выполняется через GitHub Actions;
- APK устанавливается отдельно как staging/preview;
- стартовый экран не падает без production API;
- все пункты меню открываются;
- директорский dashboard соответствует утверждённой концепции;
- роли скрывают/показывают правильные разделы;
- нет мёртвых кнопок;
- preview-функции имеют маркировку;
- LIVE-функции не используют фиктивные цифры;
- нет Telegram/Termux runtime-зависимостей;
- нет production secrets в APK;
- Android UI/security tests проходят;
- серверные regression tests проходят перед релизной веткой;
- production DB не затрагивается preview-сборкой.

## 27. GitHub Actions — регламент сборки

Эталонное место сборки APK — GitHub Actions.

Порядок:

1. Codex завершает текущую работу.
2. Проводится review diff.
3. Разрешаются конфликты.
4. Запускаются тесты.
5. Ветка синхронизируется с GitHub без потери чужих изменений.
6. Обновляется номер сборки.
7. GitHub Actions собирает staging/preview APK.
8. APK скачивается на телефон.
9. Проводится ручной UI-review.
10. Замечания фиксируются в следующую сборку.

Локальная сборка на ПК используется только как диагностический запасной путь.

## 29. Итоговая цель первой preview APK

После установки пользователь должен иметь возможность открыть приложение и визуально проверить почти весь будущий PORTAL: структуру, роли, меню, карточки, кнопки, формы, навигацию, приоритеты и дизайн.

Preview APK считается удачной, если по ней можно предметно говорить: «это поднять выше», «это убрать», «этот блок крупнее», «здесь добавить кнопку», «эта форма неудобна», «это оставить как есть» — без необходимости ждать полного backend.

---

**Этот Blueprint является визуальным регламентом будущих preview APK.**  
После завершения текущей работы Codex его следует перенести в основной репозиторий отдельным каноническим файлом и связать с `PORTAL_MASTER_ROADMAP.md` и GitHub Actions checklist.
