# PORTAL: будущий переезд телефона-сервера на Ubuntu/PostgreSQL

Это инструкция для отдельного окна миграции. После Этапа 4B отдельный тестовый экземпляр API на VPS прошёл интеграционные проверки PostgreSQL с искусственными компаниями. `PORTAL_DB_BACKEND=postgresql` допускается только при `PORTAL_ENV=test`; production по-прежнему закрыт программным ограничением. Проверенная read-only копия рабочей базы телефона уже прошла dry-run, импорт в изолированный PostgreSQL, независимую сверку и backup/restore. Production не переключался: перед cutover всё равно обязателен новый финальный снимок после остановки записей на телефоне.

## Условия до начала

1. Назначить ответственное лицо и окно обслуживания. Получить согласованную резервную копию телефона и список всех компаний/tenant DB. Закрыть запись на время финального снимка; иначе после снимка появятся операции, не попавшие на VPS.
2. На телефоне сделать backup штатным безопасным способом SQLite, сохранить исходную `portal.db` без изменений. Для каждой компании сохранить копию tenant DB и связанные файлы. Записать размеры и SHA-256 копий, сохранить второй экземпляр вне VPS. Вся дальнейшая работа идёт с копиями.
3. На отдельном Ubuntu VPS создать пользователя `portal`, каталог `/srv/portal/`, конфигурацию `/etc/portal/portal.env` (mode 0600), отдельный systemd unit и логи. Другие проекты размещать отдельно, например `/srv/projects/<other-project>/`; данные PORTAL — в отдельном PostgreSQL cluster/database и `/var/lib/portal/`, backup — в `/var/backups/portal/` и на втором независимом носителе. Создать отдельные роли владельца миграции и приложения. Не переиспользовать credentials других проектов. Включить firewall и мониторинг диска/БД/ошибок.
4. Приложение должно подключаться двумя отдельными непривилегированными DB-ролями: tenant (`PORTAL_DATABASE_URL`) и control (`PORTAL_CONTROL_DATABASE_URL`). Ни одна не имеет `SUPERUSER`, `BYPASSRLS`, владения таблицами или доступа к данным другого проекта. Tenant не получает доступ к `portal_company_keys` и таблицам Platform Owner. Миграционная роль используется только в отдельном управляемом окне. Секреты хранятся в защищённом окружении, не в Git, CLI-аргументах, логах или отчётах. Production требует HTTPS URL и отдельного разрешения программного gate после всех проверок.

## Dry-run на копиях

5. Развернуть отдельную тестовую PostgreSQL БД. Сверить фактические столбцы **копии** со схемой, затем миграционной ролью применить по порядку `server/migrations/postgresql_core_stage4b.sql`, `postgresql_stage3.sql`, `postgresql_runtime.sql`, `postgresql_rls_context.sql`, `postgresql_stage4c.sql`. Миграция контекста требует `pgcrypto`, создаёт ключи контекста для каждой компании и защищает RLS от простой подмены `portal.company_id`. Выдать tenant-роли только права на бизнес-таблицы и функции `portal_bind_company`/`portal_current_company`, control-роли — только доступ к компаниям, Platform Owner и ключам контекста. Проверить повторное применение, индексы, RLS, `FORCE ROW LEVEL SECURITY`, защитные триггеры и отсутствие доступа tenant-роли к ключам. Core покрывает известные таблицы Stage 3/4A, но реальная база может иметь дополнительные старые поля/таблицы; переносчик в таком случае должен остановиться.
6. На Linux установить `psycopg` 3 в изолированное окружение. Сначала запустить **dry-run** без доступа к PostgreSQL. Список `--tenant-copy` должен содержать каждую компанию. Отдельно передать копию `portal.db.platform.db`; если её не было до multi-company, переносчик создаст только основную компанию `PORTAL` с ID 1. Пример:

   ```bash
   python server/migrate_sqlite_to_pg.py \
     --tenant-copy 1:/secure/staging/portal.db \
     --platform-copy /secure/staging/portal.db.platform.db \
     --report /secure/staging/migration-dry-run.json
   ```

   Dry-run проверяет SQLite `integrity_check`, обязательные таблицы/поля, `company_id`, компанию 1 для старой базы без multi-company, ссылки клиента/операции, платежа/счёта и производственного ledger. Он выводит только количество записей и денежные суммы; исторические текстовые client/operation не переписываются. Устранить любые ошибки на **копии**, исследуя источник; оригинал не исправлять автоматически.
7. После успешного dry-run дать миграционной роли доступ только к пустой подготовленной БД, включая создание/чтение `portal_company_keys`, выполнение `portal_bind_company` и `USAGE`, `SELECT`, `UPDATE` для импортируемых identity sequences, и передать DSN через защищённое окружение `PORTAL_MIGRATION_DSN`. Миграционная роль не должна быть `SUPERUSER` или иметь `BYPASSRLS`; защищённую привязку компании необходимо проверить на отдельной тестовой БД до импорта копии. Выполнить ту же команду с `--apply` и отдельным JSON report. Строки переносятся в одной PostgreSQL транзакции; расхождение строк/числа/схемы даёт `FAILED` и rollback. Исходная SQLite открыта read-only. Генераторы ID повышаются после сверки строк; PostgreSQL sequence не откатывается при rollback, поэтому после любого FAILED повторять импорт только в заново подготовленную пустую БД. Сверить следующий ID до запуска сервера. Не пересчитывать старые суммы текущими тарифами и не выдавать заново номера партий.
8. Импортёр и валидатор используют защищённую привязку `portal_bind_company`; до реального импорта подтвердить её работу интеграционным тестом на отдельной пустой PostgreSQL БД. Независимо повторить read-only сверку по каждой компании, включая количество, SHA-256 строк и денежные итоги, без печати строк/секретов. Для legacy-копии без `company_id` проверить нормализацию в компанию 1; прямой валидатор предназначен для уже company-scoped копий. Дополнительные таблицы реальной базы включить в контроль. Одни совпавшие хеши не проверяют поведение API.
9. На тестовом сервере запустить полный server/API набор против PostgreSQL, включая конкурирующие партии, права и RLS, задачи, выработку и закрытый payroll, таймеры и несколько сессий, счета, частичные оплаты и изоляцию компаний. Проверить ручную финансовую сверку по периодам и компаниям. Настоящий PostgreSQL integration test обязателен до cutover; локальные тесты 4B проверяют лишь контракт и логику без PostgreSQL.
10. Настроить reverse proxy и HTTPS/домен: Android/PC-Web → HTTPS → PORTAL API (loopback) → PostgreSQL (loopback или Unix socket). Порт PostgreSQL не публиковать в интернет. Адрес API в Android задавать через `PORTAL_API_URL`/Gradle `portalApiUrl` при сборке и менять через настройки приложения; DB credentials клиентам не передавать. Проверить Android на тестовом адресе: вход, задания, «Другая работа», сотрудники, права, история входов, счета и выход. Проверить все существующие маршруты Этапа 2.

## Финальное переключение

### Проверенная тестовая процедура 26.09.2026 (без production)

Полный CLI проверен на новых искусственных SQLite-копиях двух компаний и control DB.
`server/test_migration_full_vps.py` однократно создаёт строго именованную пустую
`portal_test_migration_full_20260926` и три отдельные LOGIN-роли. Запускать только
OS-пользователем `postgres` с `PORTAL_SYNTHETIC_SETUP=1`; существующая БД или
защищённый `secrets.json` приводят к отказу, данные не очищаются.

После подготовки `server/test_migration_full_cli.py` запускается тем же пользователем
с `PORTAL_FULL_CLI_INTEGRATION=1`. Он проверяет dry-run, CLI `--apply`, независимую
валидацию, денежные суммы, 13 identity sequences, FORCE RLS, rollback при ошибке
второй компании, backup/restore в отдельную БД и API на свободном `127.0.0.1:8767`.
Работающий сервис `portal-pg-test.service` на 8766 не перезапускается.
Тест сохраняет результаты и дополнительные БД с суффиксами `_rollback` и `_restore`;
повторный запуск на заполненной БД запрещён. Не удалять их автоматически ради
повторения теста. Исходные SQLite-копии сверяются по SHA-256.

Миграционной LOGIN-роли нужны EXECUTE на `portal_bind_company(BIGINT,TEXT)` и
`portal_current_company()` (PUBLIC-доступ отозван SQL-миграцией), а control-роли —
USAGE/SELECT на identity sequences её таблиц. Эти права добавлены в тестовый fixture;
не выдавать SUPERUSER/BYPASSRLS и не делать runtime-роли владельцами таблиц.
DSN передаются дочерним CLI через окружение, не в аргументах и не в отчёте.

Все 7 сценариев прошли. Это завершает синтетическую CLI-проверку, но не подтверждает
совместимость первоначально ещё не полученной копии реальной телефонной БД. Позднее реальная копия была получена и отдельно проверена; Production gate,
проверка реальных копий, клиентские сценарии и согласованный cutover сохраняются.

11. После успешного dry-run остановить новые записи на старом сервере, сделать новый финальный backup телефона и повторить импорт/сверку на свежей копии. Если данные различаются, **не переключать** Android.
12. Поднять изолированный PORTAL Server на VPS с PostgreSQL, провести smoke test и проверить TLS. Только после полной сверки переключить адрес клиентов на VPS. Несколько часов наблюдать ошибки, задержки, операции по компаниям, резервное копирование и объём хранилища.
13. Выполнить тест восстановления backup PostgreSQL в отдельной БД. Отказ от телефона как сервера возможен только после устойчивой работы, подтверждения всех компаний и проверенного восстановления. Исходную SQLite хранить как архив согласно принятому сроку хранения.

## Backup и проверка восстановления

- Для PostgreSQL планировать регулярный `pg_dump -Fc` отдельным backup-пользователем; хранить копии в `/var/backups/portal/` с ограниченным доступом и на втором независимом носителе. Retention согласовать до запуска (например, 14 ежедневных, 8 еженедельных, 12 ежемесячных точек), шифрование и контроль свободного места обязательны.
- Пример операции в защищённом окружении: `pg_dump --format=custom --file=/var/backups/portal/portal-YYYYMMDD.dump portal`; проверка архива — `pg_restore --list /var/backups/portal/portal-YYYYMMDD.dump`. Для восстановления создать **новую тестовую БД**, затем `pg_restore --dbname=portal_restore_test /var/backups/portal/portal-YYYYMMDD.dump`; никогда не использовать рабочую БД как тест восстановления.
- Каждое задание backup проверяет exit code, ненулевой размер и доступность файла; ошибки дают сигнал оператору. Периодически восстанавливать backup через `pg_restore` в **отдельную тестовую БД**, запускать базовые проверки количества/сумм и RLS. Проверка наличия архива без тестового restore недостаточна.
- Хранить вместе с backup версию схемы, список компаний и время снимка. Не включать секреты, PIN или токены в логи и отчёты backup. Не размещать backup других проектов в каталоге PORTAL.

## Rollback

- До переключения: прекратить dry-run, оставить телефон обслуживать клиентов; исходную SQLite не менять. Ошибочную тестовую БД удалить/пересоздать только в изолированном окружении после фиксации причины.
- После переключения: остановить запись на VPS, зафиксировать новые записи для возможного обратного переноса, вернуть адрес клиентов на старый сервер по заранее проверенной процедуре. **Нельзя** молча потерять записи, сделанные на VPS после cutover, и нельзя одновременно принимать запись на обеих сторонах. Возврат требует сверки и согласованного восстановления этих операций.
- Триггеры остановки: любое расхождение строк/сумм/`company_id`, провал RLS или прав, непроходящий API/UI тест, неверный номер партии, неуспешное восстановление backup, ошибки TLS либо Android login.

## Контур будущего внутреннего чата

Чат в 4B не реализуется. Для будущего модуля использовать отдельные `messages`, `attachments`, `stickers` и `pins` с `company_id`, внешними ключами и RLS; проверять компанию и permission на сервере. Системный файл каждого «Стикера PORTAL» хранить один раз, сообщение ссылается на ID; системные файлы не входят в очистку истории. Обычные сообщения и пользовательские вложения физически удалять не позднее 14 дней. Закреплённые уполномоченным руководителем сообщения остаются до открепления; после открепления возраст снова считается от исходного времени и старые сообщения удаляются ближайшей очисткой. Очистка должна удалять blob и запись согласованно, быть идемпотентной, иметь контроль ошибок и тесты межфирменной изоляции. Legacy messaging platforms do not enter the target PORTAL APK/Desktop architecture.
