# PORTAL — обязательные правила сохранности и целостности релиза

Эти правила обязательны для ChatGPT, Codex, других агентов и человека-оператора. Они возникли после инцидента 04.10.2026: PORTAL Server 4.7.0 был запущен из правильного Git SHA, но в versioned release directory отсутствовал каталог shared Web assets. API отвечал 200, а Desktop/Web `/web/` возвращал 404.

## Главный принцип

**Нельзя считать изменение перенесённым, релиз полным или задачу завершённой по факту наличия кода в Git. Завершение подтверждается только совпадением Git → release payload → фактически запущенный runtime → smoke всех активных клиентов.**

## Непереговорные правила

1. GitHub + `PORTAL_MASTER_ROADMAP.md` — источник истины для исходников и требований. Память чата/агента является вспомогательной и никогда не заменяет репозиторий.
2. Если рабочая копия содержит чужие или незакоммиченные изменения, не смешивать их со своей задачей. Использовать отдельную branch/worktree.
3. Запрещён выборочный production deploy вида «скопировать только server» или «перенести изменившуюся папку», если runtime зависит от файлов вне неё.
4. Production/staging payload формируется из одного точного Git SHA/tag. В payload обязаны входить все runtime dependencies этого SHA.
5. До перезапуска сервиса запускать `ops/verify_release_payload.py`. Любой отсутствующий или пустой обязательный файл = NO-GO.
6. Versioned release directory после активации считается immutable. Emergency hotfix допустим только для восстановления сервиса; он обязан быть немедленно воспроизведён в Git и записан в roadmap с причиной и SHA.
7. Перед deploy фиксировать: текущий runtime SHA/release path, активные endpoint-ы, версию, backup/rollback target. Ничего старого не удалять до успешного post-deploy smoke.
8. После deploy обязательны минимум: `/api/ping`, `/api/ready`, `/web/`, критические Web assets, Desktop/Web загрузка и доступность API для мобильных клиентов. Нельзя делать вывод «сервер работает» только по `/api/ping`.
9. Любая функция считается перенесённой только после проверки на всех реально используемых контурах: VPS/API, Desktop/Web, Android и iOS, если функция для них применима.
10. Запрещено удалять, заменять или обнулять данные/тарифы/права/документы/функции ради упрощения миграции или рефакторинга без отдельного решения владельца.
11. Схемные и data migrations по умолчанию additive/reversible; перед destructive action нужны явное решение владельца, backup, reconciliation и rollback.
12. Перед заменой файла/каталога сравнивать inventory/diff. «Новая версия» не означает, что старые необходимые файлы можно не переносить.
13. После любого production incident: зафиксировать root cause, добавить regression guard, тест или gate, который не позволит тому же классу ошибки повториться.
14. Сообщать «исправлено/готово» только после фактического smoke на том endpoint-е, которым пользуется пользователь, а не только на localhost/VPS.
15. После завершения задачи: commit + push, обновление roadmap, точный SHA, список проверок и известные остаточные риски.

## Release completeness contract

Текущий shared Web runtime зависит как минимум от:

- `server/portal_app_server.py`
- `server/web_static.py`
- `android_src/app/src/main/assets/index.html`
- `ui.css`, `core.js`, `app.js`, `screens.js`, `production.js`, `preview.js`
- `invoices.js`, `documents_excel.js`, `web_adapter.js`, `brand-mark.svg`
- `stickers/catalog.json` и каталога sticker assets, если они присутствуют в текущем Git SHA

Этот перечень проверяется автоматически и должен обновляться вместе с изменением runtime contract.

## Правило остановки

Если хоть один из пунктов выше нельзя подтвердить — релиз останавливается. Лучше оставить предыдущую рабочую версию, чем запускать частично перенесённую новую.
