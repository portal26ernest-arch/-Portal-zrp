# PORTAL 3.2 — задание для Codex Sol: проект миграции и изоляции

Исходная точка: `PORTAL_3_2_BASELINE_AUDIT.md`, ветка `portal-next-b003`, commit `1fa78b0`. Аудит: 101 серверный тест пройден, 11 live PostgreSQL/VPS пропущены, Android/JS 17/17. Этот этап — только проектирование и проверяемый план; код приложения, реальные данные, миграции, тарифы и инфраструктуру не менять.

## Цель

Спроектируй безопасный переход от исторического `telegram_id` как фактического идентификатора сотрудника к устойчивому `employee_id`; одновременно определи единственный источник истины для выработки, начислений, выплат и закрытых периодов при переходе SQLite → PostgreSQL. Сохрани старые записи и денежные snapshots без пересчёта по новым тарифам. Учитывай несколько компаний и роль директора только внутри своей компании.

## Исследование исходников

1. Проследи каждое чтение, запись, JOIN и проверку прав для `telegram_id`/`employee_id` в `server/portal_app_server.py`, `portal_tenancy.py`, `production_service.py`, `production_repository.py`, `production_permissions.py`, миграторах, SQL migrations и Android `core.js`/UI. Составь таблицу `файл:место → текущий смысл → целевой смысл → совместимость → тест`.
2. Раздели три сущности: учётная запись для входа, сотрудник как субъект выработки/зарплаты и исторический Telegram ID как внешний legacy alias. Укажи уникальные ограничения и правила для отсутствующих, повторяющихся и конфликтующих алиасов, нескольких компаний и неактивных работников.
3. Выпиши физические и ledger таблицы выработки, зарплаты, выплат, счетов и периодов; обозначь authoritative source для каждой операции чтения и записи на переходном и целевом этапах. Укажи, как исключить двойное начисление при отражении legacy work_log и works.
4. Спроектируй порядок миграций SQLite и PostgreSQL, backfill, независимую сверку counts/ID/денежных итогов, dry-run и rollback. SQL для реальной БД не запускать. Закрытые payroll snapshots не изменять.
5. Проверь company scope каждого legacy API и production маршрута, SQL grants, `ENABLE`/`FORCE RLS`, binding контекста и выбор компании platform owner. Составь матрицу доступа admin/director/manager/packer и негативные тесты cross-company и коллизий ID.
6. Разбери payroll gaps из baseline: выплату зарплаты отдельно от оплаты клиентского счёта, корректировки, закрытие периодов, историю тарифов. Предложи правила состояния и аудита; неоднозначные бизнес-правила вынеси в список решений, не кодируй догадки.

## Результат

Создай `PORTAL_3_2_SOL_DESIGN.md` с конкретной схемой данных, картой API/совместимости, последовательностью маленьких реализационных шагов, тестовой матрицей, критериями GO/NO-GO и списком открытых решений. В конце дай отдельные готовые задания: Luna для механических безопасных изменений, Sol для миграций/RLS/API, Medium для payroll ledger. Каждое задание должно иметь границы файлов, критерии приёмки и запрет на реальные production записи.

Проверяй выводы по текущему коду, а не только по baseline. Не публикуй секреты, не читай значения ключей и env. Не перезапускай рабочий сервер, не меняй телефонную БД, не переключай production. Не добавляй сборку 3.2 и не меняй номер версии на этапе проектирования. По завершении сообщи созданный файл, обнаруженные блокеры и результаты только read-only проверок.
