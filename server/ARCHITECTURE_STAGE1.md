# PORTAL NEXT — b003, этап 1

Ветка: `portal-next-b003`. Сервер: `2026.09.24-a003-stage1`.
Android пока остаётся `2026.09.24-b002`: этот этап добавляет серверный фундамент,
а не новый интерфейс или готовый релиз APK. Старые маршруты и формат входа
основной PORTAL сохраняются.

## Граница изоляции

- `PORTAL_DB` по-прежнему указывает на исходную `portal.db` BOT b005.
  Основная компания имеет неизменный ID `1`, название PORTAL при создании
  и неограниченное количество активных пользователей.
- Рядом создаётся `portal.db.platform.db`: реестр компаний, отдельные учётные
  записи Platform Owner, их сессии и закрытый системный аудит.
- Сторонние компании получают `.portal-tenants/company-<id>.db` рядом с базой.
  Путь формирует сервер; клиент не может передать имя файла.
- Все таблицы данных получают `company_id NOT NULL`, значение по умолчанию
  своей компании и CHECK/триггеры, запрещающие чужой ID и NULL. Значение по
  умолчанию нужно для совместимости старых INSERT с явным списком полей.
- В каждом файле есть `portal_tenant_identity`; соединение проверяет его.
  Контекст компании хранится в ContextVar и сбрасывается после запроса,
  включая исключения. Одинаковые ID, имена и telegram_id в разных компаниях
  не объединяют данные: JOIN и старые текстовые связи остаются внутри файла.
- Старый BOT работает только с исходной `portal.db`. Его запросы без фильтра
  company_id физически не видят данные сторонних компаний или платформы.
  Прямая работа с файлами БД — доверенная операция системного оператора.

Новая компания получает только SQL-схему основной базы (таблицы, индексы,
триггеры, представления), без строк, сотрудников, доступов и токенов.
Файл создаётся исключительно новым; существующий файл не перезаписывается.
После аварии незарегистрированный файл требует проверки оператора, а не
автоматического удаления или повторного использования.

## Миграция и история

При запуске сервер проверяет существование исходной базы и обязательных
таблиц. Миграция в одной SQLite-транзакции добавляет company_id=1, таблицы
доступа при их отсутствии и маркер схемы. Существующие строки, первичные
ключи, PIN-хеши, сессии, даты, ставки, суммы, выплаты и текстовые связи не
пересоздаются. При конфликтующем company_id транзакция откатывается.
Повторный запуск безопасен. Отсутствующая portal.db не создаётся.

Обновление ставки меняет каталог для будущих записей; work_log не
пересчитывается. Переименование клиента/операции обновляет прежние
текстовые связи только в выбранной компании. Правила оплаченных периодов,
списания материалов и прогресса заданий сохранены.

Перед применением на телефоне остановить BOT/API и сделать резервную копию
SQLite штатным backup API или копированием закрытой базы вместе с её WAL,
если он существует. Проверить миграцию на копии реальной b005: её полный
DDL и код BOT в этом репозитории отсутствуют. В частности, старые INSERT
без списка колонок и распаковка SELECT * фиксированной длины потребуют
проверки со стороны BOT после добавления company_id. После миграции
возвращаться к старому серверу только с восстановлением согласованной копии.

Резервное копирование после запуска multi-company должно включать основную,
платформенную и все компании БД. Новый модуль `portal_tenancy.py` необходимо
разворачивать рядом с `portal_app_server.py`.

## Роли

| Роль API | Полномочия |
| --- | --- |
| platform_owner | Системные настройки всех компаний, закрытый аудит, явный технический доступ в выбранную компанию |
| admin | Доступы, справочники и рабочие данные своей компании |
| director | Показатели, клиенты, счета, склад, задания и собственная выработка; без управления доступами и системными параметрами |
| manager | Только назначенные клиенты, их карточки, операции, задания, счета и показатели |
| packer | Собственная выработка и зарплата, список работ и производственных заданий; без финансов клиентов |
| accountant / shift | Сохранённые роли b002: бухгалтер / старший смены, в пределах своей компании |

Личная зарплата и история `/mine` привязаны к собственному сотруднику,
а не к переданному telegram_id. Назначения менеджера применяются к клиентским
экранам и показателям, включая dashboard и фильтрацию счетов до LIMIT.
Привязка к employees обязательна для упаковщика и для внесения выработки.
Создание/импорт сотрудников и полноценный onboarding сторонних компаний —
следующий этап; новые компании не получают сотрудников основной PORTAL.

## Вход и API

Старый `POST /api/login` без company_id входит в PORTAL. Для другой компании:
`{"company_id":2,"username":"admin","pin":"..."}`. Логины уникальны внутри
компании. Новые токены содержат префикс компании и случайную секретную часть;
префикс лишь выбирает хранилище, а полный токен проверяется по сессии.
Старые токены без префикса продолжают работать только в PORTAL.

Текущую компанию определяет проверенная сессия. Подмена через заголовок,
company_id в query или теле запрещена. Приостановленная компания, отключённое
обслуживание или demo вне своего периода блокируют обычный вход и сессии.
Platform Owner может диагностировать такую компанию.

Первый Platform Owner создаётся **локально оператором**, не через APK:

```sh
python portal_app_server.py --create-platform-owner owner
```

Пароль вводится интерактивно дважды, минимум 12 символов; не передаётся в
аргументах процесса. Старые администраторы автоматически не повышаются.
Обычный `/api/users` не может создать/назначить platform_owner.

| Метод | Маршрут | Доступ |
| --- | --- | --- |
| POST | /api/platform/login | Вход отдельной учётной записью владельца |
| GET / POST | /api/platform/companies | Список / создание компании, только владелец |
| GET / POST | /api/platform/companies/{id} | Карточка / изменение, только владелец |
| GET | /api/platform/audit?after_id=0 | Закрытый журнал, страницы по 200 строк |
| GET | /api/company | Своя компания; полная карточка admin/director, краткая остальным |

Для работы владельца через обычные бизнес-API требуется
`X-Portal-Company: <id>`. Без него технический доступ отклоняется.
Он действует с правами администратора выбранной компании, но не
притворяется её сотрудником для начисления зарплаты. Так можно создать
первого admin сторонней компании через существующий `POST /api/users`.
`GET /api/me` возвращает фактическую роль platform_owner.

## Карточка компании и лимит

Поля: name, status (`active/suspended/archived`), monthly_price (целые копейки),
demo_enabled, demo_start/demo_end (локальное время сервера в ISO-формате),
user_limit, service_status (`active/suspended/expired`), created_at/updated_at.
Изменять карточку может только Platform Owner. При создании сторонней
компании лимит — 15, стоимость — 0 (не настроена), demo выключен.
Платёжная интеграция и автоматическое списание денег не входят в этап 1.

Лимит проверяется при создании активного пользователя и повторной активации.
Отключённые доступы не занимают места. Проверка сериализована SQLite-блокировкой
платформы с созданием/активацией и изменением лимита: две параллельные операции
не занимают одно последнее место. Владелец может индивидуально расширить лимит;
уменьшение ниже текущего количества активных доступов отклоняется. PORTAL
сохраняет NULL (без лимита). Платформенные владельцы не занимают места компании.

## Системный аудит

Журналируются локальное создание владельца, успешные/неуспешные технические
входы, начало и результат технических запросов, создание и изменение компаний.
Запись начала фиксируется до выполнения технической операции. Фиксируются
actor_id, company_id, время, тип события, результат, шаблон маршрута, метод,
HTTP-статус, ID объектов и названия изменённых системных полей.

Произвольные URL, query, заголовки, тела запросов, PIN, пароли, токены и
тексты исключений в журнал не попадают. Пароли владельцев хешируются PBKDF2;
их сессии действуют 8 часов и хранятся в платформенной БД только как SHA-256
хеши токенов. Обычные сессии b002 сохраняют совместимость.

API изменения/удаления аудита нет, SQL-триггеры запрещают UPDATE/DELETE.
Бизнес-база вообще не содержит глобального журнала. Это защита на уровне
приложения/SQLite, не гарантия против оператора с полным доступом к файловой
системе: права на каталог, резервные копии и сетевой доступ задаёт развёртывание.
Текущий транспорт HTTP сохранён; публичное сетевое развёртывание требует
защищённого транспорта и отдельного этапа эксплуатационного усиления.

## Проверки

```sh
python -m unittest discover -s server -p 'test_*.py' -v
PORTAL_TEST_HTTP=1 python -m unittest discover -s server -p 'test_*.py' -v
```

Тесты создают временные БД, не обращаются к базе телефона. Проверяются
совпадающие идентификаторы между компаниями, чтение/запись, подмена контекста,
роли, лимиты и гонка последнего места, закрытость аудита, отсутствие секретов,
повторная/первичная миграция, точное сохранение прежних строк и сессий,
откат при конфликтующей компании и сохранение исторических начислений.
