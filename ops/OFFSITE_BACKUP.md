# PORTAL encrypted off-site backup (operator activation)

The central backup job remains the source of record at `/srv/portal/central/backups`. It writes PostgreSQL custom dumps under `postgresql/daily`, `central-storage-*.tar.gz` under `storage/daily`, SHA-256 sidecars, then atomically publishes `central-backup-success.json` only after a complete successful run. The off-site job accepts only that fixed root, rejects stale completion (default 30 hours), rehashes every inventory entry, runs `pg_restore --list` and `tar -tzf`, and requires `portal_prod_control`, `portal_prod_company_1`, and central storage. It does not connect to PostgreSQL or read live application storage.

## External prerequisites

Install `restic`, `pg_restore`, and GNU tar from the host's approved package source. Obtain an independently administered S3-compatible repository and least-privilege credentials that can list/read/write/delete only the dedicated repository prefix. Timeweb object-storage access previously returned HTTP 403; no independent bucket/repository is currently verified. Do not treat this configuration as activated until credentials and repository are supplied and preflight succeeds.

First prepare the host from an exact current `main` SHA with `sudo ops/install_offsite_backup_ubuntu.sh --repo /srv/portal-source/repo --sha <exact-40-char-main-sha> --install-acl`. The installer creates only the isolated runtime identity, immutable tool release, systemd units and read-only backup ACLs; it never enables or starts off-site timers. Then copy `ops/offsite-backup.env.example` to `/etc/portal/offsite-backup.env`, populate it out of band, and set owner/mode `root:portal-offsite` / `0640`. Set `RESTIC_PASSWORD_FILE` to a separate file owned by `root:portal-offsite`, mode `0640`, containing a strong random client encryption password. Never put credentials in the repository URL or logs. Create the `portal-offsite` user and `portal-backup-readers` group. Grant that group read/traverse ACLs on the central backup tree (including future files); do not grant write access. The systemd units keep the source read-only and write only their private state/temp areas.

First run `sudo systemctl start portal-offsite-backup.service` only after the explicit preflight below. Preflight requires all credentials and an already initialized reachable repo. To initialize an empty repo, run `sudo -u portal-offsite env ... python3 .../portal_offsite_restic.py init --init` explicitly; this initializes only a repository and never creates a bucket. Use shell environment injection from a protected credential source, not literal command history. Then run `preflight`, followed by backup and restore-test once before enabling timers. Enable `portal-offsite-backup.timer` and `portal-offsite-restore-test.timer` only after operator review.

Backup runs daily with 45-minute random delay, retention 14 daily / 8 weekly / 12 monthly, prune, then a 5% data check. A separate weekly restore test restores `latest` for the pinned host/tag into a disposable system temp directory and validates every recorded SHA/size plus PostgreSQL dump and tar readability; it has no production restore destination. Both services share an advisory lock and systemd timeouts (2h/3h). Exit codes: 20 configuration/credentials, 21 missing/stale central success marker, 22 verification/child failure, 23 operation lock contention.

No cloud resource creation, central backup retention change, timer enablement, service restart, production restore, deployment, or release activation is performed by these scripts.
