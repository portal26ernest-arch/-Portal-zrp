# AGENTS.md — обязательный протокол PORTAL

Для любого агента, работающего с этим репозиторием (ChatGPT, Codex, GBI и другие):

1. До начала любой задачи открой и прочитай `PORTAL_MASTER_ROADMAP.md`.
2. Считай его единственным каноническим реестром требований, статусов и незавершённой работы.
3. Не начинай реализацию задачи, которой нет в разделе «Входящие / Принять в работу» или которая не была туда добавлена.
4. Перед изменениями переведи задачу в «В работе» и укажи дату/ветку.
5. После реализации обязательно обнови тот же `PORTAL_MASTER_ROADMAP.md`: результат, тесты, commit/SHA, остаток работы и следующий шаг.
6. Не храни уникальные изменения только локально. До завершения работы изменения должны быть committed и pushed в канонический GitHub-репозиторий.
7. Не выпускай релиз из боковой ветки. Release candidate обязан происходить из текущей канонической release/recovery-линии, указанной в master-файле.
8. Не удаляй утверждённые функции, тарифы, права, документы или данные ради рефакторинга без отдельного решения владельца.
9. VPS разворачивается только из зафиксированного Git commit/tag. Телефон и рабочий ПК — клиенты/рабочие терминалы, не мастер-хранилища.
10. Если фактический код расходится с master-файлом — останови релиз, зафиксируй расхождение в master-файле и сначала выполни reconciliation.
11. VPS source mirror `/srv/portal-source/repo` является только серверной копией GitHub, не отдельной веткой истины. Перед серверной работой синхронизируй его через `ops/sync_vps_source_mirror.sh` с веткой/commit, указанными в master-файле; скрипт обязан отказать при локальных изменениях.
12. Для любой общей мобильной функции соблюдать Android ↔ iOS parity: shared UI/Server contract меняется один раз для обеих платформ; нативные различия реализуются на обеих оболочках, если функция применима. Одноплатформенное изменение допускается только по явному решению владельца или объективному ограничению ОС. Перед завершением мобильной задачи обязательны Android и iOS CI/gates.
13. Перед любой работой с dirty worktree не смешивать чужие/незакоммиченные изменения со своей задачей: создать отдельную branch/worktree.
14. Любой deploy обязан переносить полный runtime payload одного точного Git SHA/tag. Запрещено выборочно копировать только `server/` или отдельные изменённые каталоги, если runtime зависит от shared assets.
15. До рестарта staging/production обязательна fail-closed проверка `ops/verify_release_payload.py`. После рестарта обязательны smoke `/api/ping`, `/api/ready`, `/web/` и критических Web assets на фактическом пользовательском endpoint.
16. Нельзя сообщать «готово/исправлено» только по локальному тесту или одному health endpoint. Нужно подтвердить фактически используемые VPS/API, Desktop/Web и применимые Android/iOS контуры.
17. Активированный versioned release считается immutable. Emergency hotfix на VPS допустим только для восстановления сервиса; затем он немедленно переносится в Git, фиксируется в roadmap и получает regression guard.
18. После любого production incident обязательно записать root cause и добавить автоматический тест/gate против повторения этого класса ошибки.
19. Полный обязательный регламент сохранности и релизной целостности находится в `PORTAL_RELEASE_INTEGRITY_RULES.md`; он обязателен наравне с этим файлом.
20. Каноническая ветка исходников — `main`. Боковые ветки допустимы только как временная изоляция работы; завершённые изменения обязаны быть проверены, зафиксированы в roadmap, pushed и интегрированы в `main`.
21. VPS source mirror `/srv/portal-source/repo` должен автоматически синхронизироваться с GitHub `main` через `portal-source-sync.timer`. Расхождение source mirror и `origin/main` считается инцидентом сохранности.
22. Автосинхронизация исходников не означает автоматическую активацию production: staging/production runtime всегда разворачиваются полным immutable payload одного точного SHA после соответствующих CI/release gates. Так мы одновременно исключаем потерю файлов и не выкатываем непроверенный код пользователям.

Любые другие отчёты и документы считаются справочными. Если они противоречат `PORTAL_MASTER_ROADMAP.md`, приоритет имеет `PORTAL_MASTER_ROADMAP.md`.
