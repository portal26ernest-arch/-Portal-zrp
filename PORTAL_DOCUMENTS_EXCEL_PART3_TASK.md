# PORTAL — Documents + Excel, Part 3

Дата: 29.09.2026
Ветка: `codex-documents-excel-part3`
База: `64ea667` — проверенный Documents + Excel Part 2.

## Цель
Довести пользовательский контур документов после Part 2: безопасное системное «Поделиться», отправка на email через Android intent без SMTP-секретов, PDF «Счёт на оплату» и краткий A4/PDF расчётный лист сотрудника.

## Обязательные исходные материалы
Перед изменениями прочитай:
- `PORTAL_DOCUMENTS_EXCEL_PART2_REPORT.md`
- `PORTAL_MASTER_ROADMAP.md`
- текущий native bridge в `MainActivity.java`
- `documents_excel.js` и существующие server Documents/payroll/invoice API.

Не ломай Part 2: Documents list/filter/archive/download, Excel blank/prefill, preview/apply/result и tenant isolation должны продолжить работать.

## Android Share / Email
1. Добавь безопасный native bridge для передачи готового файла в системный Android Share Sheet.
2. Используй только `content://` URI через FileProvider/эквивалент; `file://` наружу запрещён.
3. Сохрани строгий allowlist MIME/расширений и лимитов; не выдавай широкие storage permissions.
4. Файл для шаринга размещай во внутреннем cache/app storage и выдавай только временное read permission.
5. Открывай системный chooser. Никакой скрытой автоматической отправки.
6. Добавь возможность передать необязательный email получателя и тему/текст в intent.
7. Не внедряй SMTP/API и не сохраняй почтовые пароли/токены.
8. UI: «Поделиться» для ready-документов, Excel-шаблонов и безопасного import result; архивные документы не шарить.
## PDF и расчётные документы
9. Реализуй server-side генерацию PDF для существующего «Счёт на оплату» на данных выбранной компании/клиента/счёта.
10. Термин в интерфейсе и документе: «Счёт на оплату».
11. PDF счёта должен брать реквизиты исполнителя и клиента из существующих данных, позиции операции/количество/цена/сумма и итог. Не подменяй отсутствующие данные выдуманными.
12. Реализуй краткий A4/PDF «Расчётный лист» сотрудника без детализации по клиентам/операциям.
13. Поля расчётного листа: компания, «Расчётный лист», период/год, ФИО, итоговая сумма, дата.
14. Подписи строго в порядке: Управляющий компанией → Управляющий подразделением → Сотрудник.
15. Генерация должна опираться на существующие payroll snapshots/закрытые периоды и не менять финансовые факты.
16. Сгенерированные PDF регистрируй в существующем Documents-контуре с company/employee/client scope, метаданными, безопасным filename и неизменяемой историей.
17. Добавь/используй отдельные авторизационные проверки; сервер остаётся окончательным источником tenant isolation.
18. Если текущая архитектура не позволяет безопасно сделать один из генераторов без крупной миграции, реализуй безопасный минимальный вертикальный срез и явно зафиксируй остаток в отчёте, не ставя ложный статус ✅.

## UI
19. Добавь реальные, не мёртвые действия для генерации/скачивания/шаринга PDF там, где соответствующие данные уже доступны.
20. Для Platform Owner сохраняй обязательный явный выбор компании.
21. Для директора/администратора доступ только своей компании по существующим capabilities.
22. Ошибки показывай безопасно, без stack trace/секретов/SQL.
23. Не добавляй fake/preview данные в production UI.

## Безопасность и ограничения
24. НЕ разворачивай ничего на VPS/production.
25. НЕ меняй production DB, телефонную SQLite, тарифы, зарплатные факты или закрытые payroll snapshots.
26. НЕ делай production APK/signing/version bump в этой задаче.
27. НЕ возвращай Telegram/Termux runtime-зависимости.
28. Не ослабляй RLS, auth, capabilities, idempotency и file validation.
